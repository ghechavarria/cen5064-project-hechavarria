# ADR-012: Account sign-in and library sync with Supabase (email sign-up)

**Date:** 2026-11-07
**Status:** accepted. Scope change decided by the developer: core feature 4 was "Sign in with a Google account"; it is now email sign-up and log in. The instructor was not asked (developer's decision).

## Context

Core feature 4 is "keep your library synced and backed up to your account across sessions and devices." The app is run in Expo Go so that anyone can run it on an iPhone or an Android phone for free (ADR-005). Google sign-in needs a native library that Expo Go cannot load: it would require a custom development build, and installing that on someone else's iPhone needs Apple's paid Developer Program. Syncing across devices also needs a store outside the phone.

## Decision

- **Accounts:** email and password sign-up and log in through Supabase (free tier), with its JavaScript client (`@supabase/supabase-js`). It runs inside Expo Go on both platforms with no native build. Rejected: Google sign-in with a development build (not free on iPhones); writing our own auth server (passwords, hashing, reset emails and hosting are far more work and more risk).
- **Links in emails:** links in Supabase's emails do not return reliably into Expo Go, and on the free plan the email templates cannot be edited to carry a code instead. So email confirmation is **off** (an account can be used as soon as it is created) and password reset is left out for now; it can return with custom email (SMTP) settings.
- **Session on the phone:** kept in AsyncStorage (built into Expo Go). Supabase's encrypted-storage recipe needs extra native code, so it is not used; the refresh token is stored unencrypted on the device.
- **Data:** the phone's SQLite stays the working copy (ADR-002). One Supabase table holds a synced copy per account, protected by row level security so each account can read and write only its own rows; that is also why the public (anon / publishable) key may ship in the app. The service_role key is never used. This adds a second store to the "one data store" constraint.
- **Sync rule:** offline-first. Sync runs on sign-in, on app start when signed in, and after each change. Every stored book has an `updatedAt`; per book, the latest change wins. Deletes are soft (a `deletedAt` tombstone), so a book deleted on one phone never comes back from the other.
- **Identity:** the Supabase user id becomes the `ownerId` (it was the fixed `"local"`). On the first sign-in on a phone, the local library moves under the account, and a book present in both adds its copies (the duplicate-ISBN rule). Signing out keeps a local library working.
- **Architecture:** Service owns the ports (`Accounts`, `LibraryBackup`, `SyncStore`) and the use cases; Data has the Supabase adapters behind one small wrapper class; only `bootstrap.ts` creates the Supabase client. If the project URL or key is missing, the app runs normally and the account screen explains that sync is not set up (a Null Object, no crash).

## Consequences

Feature 4 is free and runs in Expo Go on both platforms, and the run steps do not change. The cost: a Supabase project to create and keep awake (free projects pause after about a week without activity, so it must be resumed before grading), a second store holding a copy of the library, and the scope wording changing from "Google account" to "account". The shared project's URL and publishable key are built into the app, so a person following the README needs no Supabase setup (`.env` can point at another project). Email confirmation: **off**, because the free email sender only reaches the project's own team members. A signed-out phone shows no books and cannot scan; changes reach other phones through Supabase Realtime (known issue: a delete made in the browser reached the other device only after **Sync now**; outstanding).
