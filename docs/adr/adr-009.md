# ADR-009: Ports and adapters between Service and Data

**Date:** 2026-10-10 (recording a decision made in Sprint 4, 2026-09-21)
**Status:** accepted

## Context

The use cases need to save books and look up ISBNs, but the storage differs by platform (SQLite on a phone, browser storage on the web, memory in tests) and the book sources changed during the semester (ADR-003, ADR-006). If Service imported those classes directly, every such change would ripple into the business logic, and the logic could only be tested with a real database and network.

## Decision

The Service tier owns two interfaces, `BookRepository` and `IsbnLookup`, in `service/ports.ts`. The Data tier implements them (`SqliteBookRepository`, `JsonBookRepository`, `MemoryBookRepository`; `OpenLibraryIsbnLookup`, `GoogleBooksIsbnLookup`, combined by the `MergedIsbnLookup` and `CachingIsbnLookup` decorators). `CompositionRoot` in `bootstrap.ts` is the only place that names the concrete classes. `tests/architecture.test.ts` fails the build if Service imports Data or calls `fetch`.

## Consequences

Storage and sources can change without touching a use case: adding Google Books in Sprint 6 meant one new adapter and one line in `CompositionRoot`. Every use case and user flow is tested in seconds with in-memory fakes. The cost is one extra interface file and a composition root to read when tracing a call.
