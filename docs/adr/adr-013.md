# ADR-013: Incremental sync, a self-healing Realtime watch, and pull to refresh

**Date:** 2026-11-15
**Status:** accepted. Extends ADR-012; its "latest change wins" rule is unchanged.

## Context

Two problems came out of using and reviewing feature 4. In the peer review (issue #20), Yousef Habouh found that every sync downloaded the whole library and compared it book by book, even after a change to one book. And the outstanding auto-sync bug from ADR-012 (a delete made in the browser reached the other phone only after **Sync now**) traced back to the Realtime watch. A channel could fail and never be noticed, for example when the phone sleeps or changes network, or when it joins before the sign-in token is ready and the database refuses its filter. A change made during that gap was never announced. The owner also wanted to pull a book list down to sync it.

## Decision

- **Server stamp:** `library_books` gets a `synced_at` column (milliseconds), set by a database trigger on every write, never by a phone, because phone clocks can be wrong. The same trigger skips an update that is not newer than the stored row (`updated_at`), so a late upload can't overwrite a newer change and resending one does nothing (`supabase/migrations/20261115000000_library_books_synced_at.sql`).
- **Incremental sync:** the phone keeps a cursor per account, the newest `synced_at` it has seen. A sync fetches only rows stored after the cursor (starting 30 s earlier, so a row whose write committed late isn't missed; rows seen twice are ignored). It sends only the books marked **unsent**, which are those saved or deleted on this phone since they were last sent. The first sync of an account on a phone has no cursor, so it compares the whole library as before. Pages are read by key (`synced_at`, then ISBN), not by position.
- **Ports:** `SyncStore` adds `unsentVersions`, `markSent`, `syncCursor` and `saveSyncCursor`, and `applyVersions` returns how many versions it stored. `LibraryBackup.pull(ownerId, since)` returns the versions and the next cursor. The Memory, JSON and SQLite stores implement them (SQLite adds an `unsent` column and a `sync_cursors` table on upgrade).
- **Self-healing watch:** `LiveChanges` (Data) reopens the Realtime channel after a failure or a refusal (2 s, doubling to 1 min). Each time the database confirms the channel is live, it asks for a sync, so anything missed while it was down is caught up. That catch-up is cheap now that a sync downloads only what changed.
- **Pull to refresh:** pulling To be read, Owned or Wanted down while signed in runs a sync (`LibraryAppModel.refresh`, `PullToSync`). If the account can't be reached, the list stays as it is and a banner says it will sync later.

## Consequences

A sync now moves only what changed, so syncing after every change stays cheap as a library grows. Auto sync recovers by itself from dropped or refused channels. The cost is a second SQL file the project owner must run once, an `unsent` flag and a cursor on every phone, and a 30 s overlap that re-reads a few rows. The bug fix is a diagnosis plus a defence: the exact failure wasn't reproduced on the phones, so the two-phone check (a delete made in the browser appears on the phone without a tap) has to be redone. Revisit if Supabase adds a change feed that can be replayed after a gap.
